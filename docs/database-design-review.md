# データベース設計レビュー

## 目的

本ドキュメントは、現行のデータモデルおよび履歴機能を前提として、初回デプロイ前に確認・対応しておきたいデータベース設計上の論点を整理する。

対象は「本番データが蓄積してから変更すると移行コストが高くなるもの」を優先し、UI改善や将来機能の詳細設計は含めない。

## 現状の前提

- 定義層: `record_items` / `record_fields`
- 記録層: `records`
- 値層: `record_values`
- `daily` 項目は `save_record` RPC で upsert、`multiple` 項目は insert
- `record_values` は型別カラムを持ち、トリガーで定義との整合性を検証
- 履歴は `get_record_history` RPC で日付ページングし、クライアントの `buildHistoryCards` で日別・項目別に要約
- `record_fields.history_aggregation` と `unit` により履歴表示の集約方法と単位を定義

履歴機能の責務分離と拡張方針は現状のままで問題ない。以下は、その前提を崩さずにデプロイ前の安全性を高めるための検討事項である。

---

## デプロイ前に対応したい事項

### 1. 定義削除時に過去記録を連鎖削除しない

#### 現状

以下の外部キーが `ON DELETE CASCADE` になっている。

- `records.item_id -> record_items.id`
- `record_values.field_id -> record_fields.id`

そのため、記録項目やフィールド定義を物理削除すると、過去の記録または値も削除される。

#### 方針

ライフログでは、入力対象として使わなくなった定義と過去記録を分けて扱う。

- 項目・フィールドは原則として物理削除しない
- 入力対象から外す場合は無効化する
- 過去記録は無効化後も履歴に表示する

`record_items` には既に `is_active` があるため、`record_fields` にも `is_active boolean not null default true` を追加する。

#### 対応候補

- [ ] `record_fields.is_active` を追加する
- [ ] 入力用取得処理では無効フィールドを除外する
- [ ] 履歴RPCでは無効フィールドも過去値として表示する
- [ ] 記録が存在する項目・フィールドの物理削除を禁止する
- [ ] 必要に応じて外部キーの削除動作を `RESTRICT` に変更する

#### 完了条件

項目またはフィールドを入力画面から非表示にしても、既存の履歴が失われない。

---

### 2. 記録済み定義の意味を変える更新を禁止する

#### 現状

履歴表示は現在の `record_items` / `record_fields` を参照する。

そのため、過去記録が存在する定義について次を変更すると、過去記録の意味まで変化する。

- `record_items.frequency`
- `record_fields.value_type`
- `record_items.item_key`
- `record_fields.field_key`

特に `frequency` を `multiple` から `daily` に変更すると、既存データが1日複数件存在する可能性がある。また、`records.frequency` に転記済みの値との不整合も生じる。

#### 方針

記録が1件でも存在する定義について、識別子・値型・頻度の変更を禁止する。

意味を変えたい場合は、旧定義を無効化して新しい項目またはフィールドを作成する。

表示上の変更は許可する。

- 許可: `name`, `label`, `sort_order`, `unit`, `is_active`
- 条件付きで許可: `min_value`, `max_value`, `max_length`, `is_required`, `history_aggregation`
- 記録存在時は原則禁止: `frequency`, `value_type`, `item_key`, `field_key`

#### 対応候補

- [ ] 記録済み項目の `frequency` 変更をDBで拒否する
- [ ] 記録済みフィールドの `value_type` 変更をDBで拒否する
- [ ] `item_key` / `field_key` の変更可否を明示する
- [ ] 定義更新を直接UPDATEではなくRPC経由に寄せるか判断する

#### 完了条件

既存履歴の意味を破壊する定義更新が、フロント実装に依存せずDB側で防止される。

---

### 3. `recorded_at` の意味を確定する

#### 現状

`records` には以下がある。

- `recorded_on`: 記録対象日
- `recorded_at`: 記録日時
- `created_at`: 行作成日時
- `updated_at`: 行更新日時

`daily` 項目を再保存すると、`recorded_at` は新しい保存時刻で更新される。

そのため、現在の `recorded_at` は「出来事の発生時刻」ではなく「最後に記録した時刻」に近い。

#### 論点

将来、以下を記録したくなる可能性がある。

- 飲酒した時刻
- 歯磨きした時刻
- 服薬した時刻
- 入力は翌日だが、出来事は前日の特定時刻

#### 推奨方針

現時点では以下の意味に固定する。

- `recorded_on`: 記録対象日
- `recorded_at`: ユーザーが保存操作を行った時刻、または最終入力時刻
- `created_at`: DB行の初回作成時刻
- `updated_at`: DB行の最終更新時刻

出来事の時刻が必要になった場合は、`occurred_at timestamptz null` を追加する。

初回デプロイ時点で時刻別分析を行わないなら、`occurred_at` の追加は必須ではない。ただし `recorded_at` を発生時刻として扱わないことをドキュメントに明記する。

#### 対応候補

- [ ] `recorded_at` の意味をREADMEまたはDBコメントに明記する
- [ ] `occurred_at` を初回デプロイ前に追加するか判断する
- [ ] 履歴の並び順に `recorded_at` を使うことが適切か確認する

#### 完了条件

入力時刻・更新時刻・出来事の時刻が混同されない。

---

### 4. 記録・値の書き込み経路をRPCに限定するか決める

#### 現状

`authenticated` ロールには、以下4テーブルへの `SELECT / INSERT / UPDATE / DELETE` が付与されている。

- `record_items`
- `record_fields`
- `records`
- `record_values`

一方、必須フィールドが揃っていることの検証は `save_record` RPC の処理末尾で行われる。

そのため、`records` と `record_values` を直接操作すると、RPCの保証を経由しない不完全な記録を作成できる余地がある。

#### 推奨方針

記録データについては、以下のように責務を分ける。

- 読み取り: テーブルまたは履歴RPC
- 保存: `save_record`
- 編集: 保存仕様に応じたRPC
- 削除: 専用RPC

`records` / `record_values` のクライアントからの直接書き込み権限は外す方向を推奨する。

定義層の直接更新についても、前項の変更制約をDBで保証するなら、専用RPCへの集約を検討する。

#### 対応候補

- [ ] `records` / `record_values` の直接書き込み権限を外すか判断する
- [ ] multiple記録の編集RPCを用意するか判断する
- [ ] 記録削除RPCを用意する
- [ ] 定義更新・無効化・並べ替えをRPCに集約するか判断する

#### 完了条件

アプリが想定する保存ルールを迂回して、不完全または不整合な記録を書き込めない。

---

### 5. daily保存の同時実行時の挙動を確認する

#### 現状

`save_record` はdaily項目について次の順序で処理する。

1. 既存記録を検索
2. 存在すれば更新
3. 存在しなければinsert

部分ユニークインデックスにより重複行は最終的に防止されるが、同一日・同一項目への保存が同時実行された場合、片方がunique violationになる可能性がある。

#### 方針

個人用アプリで発生頻度は低いが、二重送信や複数端末を考慮し、少なくとも挙動をテストする。

#### 対応候補

- [ ] 同一daily項目を同時保存するDBテストを追加する
- [ ] unique violationを許容してUIで再試行するか決める
- [ ] 必要ならadvisory lock等でsave_recordを直列化する
- [ ] 保存ボタンの二重送信防止をフロントに入れる

#### 完了条件

同時保存で重複データが作られず、利用者に理解不能な状態が残らない。

## 履歴機能に関する確認事項

### 6. 無効化した定義を履歴に残す

現行の `get_record_history` は、`record_items.is_active` でフィルタせず、無効化した項目の過去記録も返す。これは履歴用途として適切であり、維持する。

`record_fields.is_active` を追加する場合も、履歴RPCでは過去値に紐づく無効フィールドを除外しない。

- [ ] 入力用取得と履歴用取得で `is_active` の扱いを分ける

---

### 7. 集約定義変更時の過去履歴表示

#### 現状

`record_fields.history_aggregation` は現在の定義を履歴RPCが返すため、値を変更すると過去のカード表示も変わる。

例:

- `none` から `sum` へ変更すると、過去の各回表示が合計表示になる
- `unit` を変更すると、過去の数値にも新しい単位が表示される

#### 方針案

初期段階では、履歴表示ルールを現在の定義に追従させる。

ただし、単位の意味そのものが変わる変更は行わない。

- 表記変更: 許可（例: `点` の表示調整）
- 値の尺度変更: 旧定義を無効化し、新しいフィールドを作成

厳密な履歴再現が必要になった場合のみ、記録時点のラベル・単位・集約設定をスナップショットとして保持する設計を検討する。

- [ ] 初回デプロイでは「履歴表示は現在の定義に追従」と明記する

---

### 8. 項目名・フィールド名変更時の履歴表示

項目名やラベルの変更も、現状では過去履歴へ反映される。

個人用アプリでは扱いやすいため、この挙動を採用する。

ただし、意味が変わる名称変更は避け、別定義として作る。

- [ ] 名称変更は過去履歴にも反映される仕様として明記する

## 初回デプロイ前のDB検証項目

以下は、設計変更とは別に実施したい動作確認である。

### マイグレーション

- [ ] 空のローカルDBへ全マイグレーションを順番に適用できる
- [ ] `supabase db reset` が成功する
- [ ] 既存ユーザー向けの `history_aggregation` / `unit` バックフィルが意図どおり動く
- [ ] 本番Supabaseプロジェクトへ `supabase db push` できる

### 認証・初期データ

- [ ] 新規ユーザー作成時に初期項目・フィールドが作成される
- [ ] 別ユーザーのデータをRLS経由で閲覧・更新できない
- [ ] 初期項目作成トリガー失敗時のサインアップ挙動を確認する

### 記録保存

- [ ] daily項目の初回保存が成功する
- [ ] daily項目の再保存で同じrecordが更新される
- [ ] multiple項目を同日に複数保存できる
- [ ] 必須フィールド不足が拒否される
- [ ] 値型不一致、min/max超過、max_length超過が拒否される
- [ ] 他ユーザーのitem_id / field_idを渡した保存が拒否される

### 履歴

- [ ] 記録のある日だけが新しい順で返る
- [ ] 日付単位でページングされ、同日の記録が分割されない
- [ ] `has_more` が正しい
- [ ] 純アルコール量が日別に合計される
- [ ] 歯磨きの点数が各回表示される
- [ ] 無効化した項目の過去記録が表示される
- [ ] 項目名・ラベル・単位変更後の過去表示が想定どおりである

### 削除・無効化

- [ ] 項目を無効化しても過去記録が残る
- [ ] フィールドを無効化しても過去値が残る
- [ ] 物理削除が必要な場合の挙動を確認する

## デプロイ前の推奨優先順位

### P0: 本番データ投入前に方針決定・対応

1. 定義削除で過去記録を失わない
2. 記録済み定義の `frequency` / `value_type` 変更を禁止する
3. `recorded_at` の意味を確定する
4. 記録層・値層の書き込み経路をRPCに限定するか決める

### P1: 初回デプロイ前に検証

5. daily保存の同時実行
6. RLSと他ユーザーIDを使った不正保存
7. 全マイグレーションの新規環境適用
8. 無効化後も履歴が残ること

### P2: 初回デプロイ後でも対応可能

9. 定義の本格的なバージョン管理
10. 記録時点のラベル・単位・集約定義のスナップショット
11. ユーザーごとのタイムゾーン設定
12. 日別集計テーブルやキャッシュ

---

## 現時点の結論

現行の3層構造、保存RPC、整合性トリガー、履歴RPCとクライアント集約の分担は維持してよい。

初回デプロイ前に最も重要なのは、次の2点である。

1. 定義を編集・削除したときに過去履歴の意味やデータを壊さないこと
2. `save_record` が保証しているルールを、直接テーブル操作で迂回できないこと

これらを固めた後であれば、集約方法の追加、入力UI、履歴表示の改善などはマイグレーションと再デプロイで段階的に対応できる。
